# 内容同步性能评估（2026-09-10）

结论：两个方向仍有潜在优化空间，但本次样本的主要成本是工作簿解析和保存，
并非身份匹配。保留当前 openpyxl 实现，不增加 pandas 或并行依赖，不改业务规则。
本记录完成 PERF-01 评估；它不是新的业务契约。

## 复现

```powershell
python scripts/benchmark_content_sync.py --repeat 3 > build/sync-benchmark.jsonl
# 可选：需要桌面 Excel，只操作自动生成的临时样本
python scripts/benchmark_content_sync.py --case resave
```

[基准脚本](../../scripts/benchmark_content_sync.py)每轮使用独立 Python 进程和临时目录，
生成来源与目标内容不同的工作簿，执行原位同步并断言更新格数及零失败；结束后清理样本。
默认运行两个方向的大表、多文件、公式场景，以及正向多列场景，各 3 轮。
`--include-resave` 在完整基准末尾加入原生 Excel 重存。

环境：Windows 10 x64（19045）、Python 3.11.6、openpyxl 3.1.5、本机临时目录。
以下为 3 轮耗时中位数，内存取 3 轮峰值的最大值。计时从业务调用开始，不含生成样本；
嵌套计时扣除子阶段，带少量测量开销。阶段中位数之和不一定等于总耗时中位数。
日志使用 GUI 的有界 LogBuffer，测量格式化和入队，不包含弹窗绘制。
内存是整个 Python 进程峰值 RSS，包含导入和样本生成，不含独立 Excel 进程。

可选重存的独立 Excel 会话启动/退出中位数为 1.476 秒，5 个文件原生重存为 .789 秒；
这部分通常比小样本同步本身更贵。来源索引包含公式校验和重复身份处理；
反向跨文件合并等剩余编排单独计入脚本的 `orchestration`。

## 决策与边界

- 现有实现已在正向复用 Master 索引、反向汇总后仅保存一次 Master；无变化时也已避免重写原文件。
- 多小表正向成本随文件数显著增加，保存成为最大项。pandas 不能省去保留原目标样式、公式、VBA 所需的编辑与保存；仅加速匹配的理论收益在这些样本中有限。
- 带公式来源存在第二遍缓存解析成本。直接只读缓存会丢失“无缓存公式与真实空白”的区别；不能为提速删除校验。
- 并发处理不同小表可能提高吞吐，但会增加内存和磁盘竞争，反向还须保持后文件优先及冲突来源顺序。没有这些保证和代表性实测前不启用并行；不并发写同一 Master 或共享 COM 实例。
- 下一次针对真实慢文件优化时，优先复现带大量样式/特殊对象/稀疏行的读写热点，再比较有限并发或专门的公式读取路径。没有用户原始慢样本，本轮不声称适用于所有工作簿。

本次没有生产代码优化，因此无“优化后加速百分比”。全量回归 513 项通过（13 项环境相关跳过），
涵盖空白与文本、公式缓存、冲突顺序、失败保护和 GUI 日志；当前规则见[内容同步 README](../../tools/content_sync/README.md)。
