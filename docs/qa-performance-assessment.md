# QA 检查性能评估

评估及优化日期：2026-09-16。优化前业务代码基线：`3db6de8`。
已完成下列优化，目标是保持检查判定及最终报告契约不变。

## 已实施的优化与回归复查

- 双向一致性：独立报告按组复用符合 Excel 长度上限的行号字符串；工作流跳过最终不会
  展示的同组行号内容，避免大量重复截断和分配。
- 全部单项检查：共用已有数据行的有序索引，读取缺失单元格时不创建空单元格；保留原始
  行号，以及开始行至最后有值行的总行数口径。
- 术语：使用本行增量覆盖层，整行通过后提交；冲突时丢弃全部本行新增和空 Target 补全。
- 子串：普通数据继续使用 Aho-Corasick；位置命中过密时切换首个有效匹配查找，保留全部
  不同子串关系、ASCII 词边界及原有报告描述顺序。
- 小项：Target 文本规则配置只校验一次；数字没有屏蔽区间时复用文本，数字 / URL
  判定与报告复用 Counter。未引入跨任务文本缓存或工作簿并发写入。

### 同机交替对照

使用归档的基线代码与修改后代码，每次启动独立进程，按“旧、新”交替测量。
常规组重复 3 次取中位数；大分组完整流程和密集子串各测一次，避免把单次结果当作稳定阈值。
RSS 口径同下文，包含解释器、输入和输出对象，工作流还保留造数工作簿。

| 场景 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 8,000 行同 Source 分组，单项检查 | 0.908 秒 / 561.5 MiB | 0.656 秒 / 60.8 MiB | 独立报告行号内容不变 |
| 8,000 行同 Target 分组，单项检查 | 0.986 秒 / 561.4 MiB | 0.669 秒 / 60.9 MiB | 独立报告行号内容不变 |
| 5 万行、1 万词条，术语检查 | 7.232 秒 | 2.451 秒 | 均输出 10,000 条术语、3,800 个问题 |
| 1 万行普通文本，全部检查完整流程 | 2.368 秒 | 2.093 秒 | 包含加载、检查、统一报告和保存 |
| 8,000 行同 Source 分组，全部检查完整流程 | 3.115 秒 / 607.7 MiB | 2.010 秒 / 106.4 MiB | 单次对照 |
| 800 行高度重复文本，子串检查 | 56.083 秒 | 1.368 秒 | 单次对照；均为 0 个问题 |

“Target 为空”本轮未修改，其测试数值的小幅变化反映环境波动；不能把所有跨批次耗时差
都归因于代码优化。完整流程的普通数据收益约 12%，边界场景的内存收益更明显。

稀疏场景复测：跨度 10 万行、两条实际数据，所有检查均保留原表的 6 个单元格，额外
单元格仅来自输出表头；单项耗时约 0.003–0.006 秒，进程峰值约 43–44 MiB。
这些毫秒级数字包含调用入口开销，仅作数量级参考；不再扩张输入表是确定的结构性改进。

## 范围与方法

覆盖一键检查的全部 11 个检查类别，采用各项默认规则配置，并将 Target 文本规范的 5 条规则拆开测量。
数字和 URL 分别测量；完整工作流中仍按现有实现合并执行。
业务规则以 [workflow README](../tools/workflow/README.md) 和各工具 README 为准。

使用 [benchmark_qa.py](../scripts/benchmark_qa.py) 生成合成工作簿，每次测量启动独立
Python 进程，顺序运行，避免基准任务之间争抢 CPU。普通场景每组重复 3 次，报告中位数。

- 环境：Windows 10 build 19045、Python 3.11.6、openpyxl 3.1.5，已安装 pyahocorasick；
  Intel64 Family 6 Model 151，16 个逻辑处理器。未控制其他应用、磁盘缓存或处理器频率。
- 普通场景：1 万 / 5 万行、Source/Target 两列、100 个标记术语；每 4 行共享 Source，
  约三分之一含 XML tag、占位符、双引号、换行和 URL。向 10% 的行注入 5 类缺陷。
  注入比例不是某项检查的命中率；同一行可能触发多个检查。
- 单项耗时：已加载工作簿，包含规则计算和未格式化的临时问题表，排除造数与磁盘读写。
  独立工具的完整格式化和保存成本不在单项数字中。
- 工作流耗时：包含加载、全部所选检查、合并报告、格式化和保存；排除造数及输入文件首次保存。
- RSS 是进程峰值，包含解释器、输入数据和输出对象，不能当作规则的增量内存。
  工作流测试还保留了造数工作簿，因此 RSS 高于仅运行实际工作流时的占用。
- `--profile` 仅定位调用热点，带 profiler 的耗时不与普通基准直接比较。
  新增 CPU 时间、结果计数是诊断字段；首批记录没有这些字段。

这些数据用于定位瓶颈，不构成真实项目的耗时承诺。历史 TB 文件加载、用户自定义正则、
缺失 pyahocorasick 的回退路径、复杂格式 / 公式 / 多工作表文件未纳入本轮计时。

## 边界场景

### 超大一致性分组

所有行共享一个 Source、交替使用两个 Target；反向场景交换两列。
没有 Excel 加载和保存，3 次中位数。

| 同一分组行数 | 正向耗时 | 反向耗时 | 正 / 反向最高峰值 RSS |
|---|---:|---:|---:|
| 1,000 | 0.031 秒 | 0.030 秒 | 45.9 MiB |
| 2,000 | 0.084 秒 | 0.076 秒 | 48.1 MiB |
| 4,000 | 0.246 秒 | 0.275 秒 | 52.5 MiB |
| 8,000 | 1.180 秒 | 1.074 秒 | 561.3 MiB |

根因在两个一致性检查的 `grouped_rows`：组内全部行号组成一个长字符串后，写入每一条
问题记录。openpyxl 的 `Cell.check_string` 每次赋值都执行 `value[:32767]` 和非法字符扫描；
8,000 行的组号串超过单元格长度限制，每个单元格都会产生新的截断字符串。
正向中位数运行里，临时问题表就占 1.135 / 1.180 秒。

统一工作流的 `collect_review_rows` 又会忽略“同组行号”列，因而工作流承担了不必要的
构造成本。单工具报告需要保留这列，优化时应区分两种输出契约。

### 稀疏表

只有两条数据，分别位于第 2 行和第 100001 行，初始仅 6 个单元格（含表头）。
此压力场景各项运行一次，时间只作数量级参考。

| 检查 | 耗时 | 完成后工作簿单元格数 | 峰值 RSS |
|---|---:|---:|---:|
| 术语 | 0.784 秒 | 200,015 | 93.3 MiB |
| 正向一致性 | 0.373 秒 | 100,010 | 68.4 MiB |
| 反向一致性 | 0.423 秒 | 100,010 | 68.3 MiB |
| 子串 | 0.294 秒 | 100,008 | 69.4 MiB |
| Tag | 1.688 秒 | 200,037 | 93.1 MiB |
| 换行 | 0.643 秒 | 200,009 | 93.3 MiB |
| 数字 | 2.219 秒 | 200,010 | 93.3 MiB |
| URL | 1.196 秒 | 200,010 | 93.4 MiB |
| Target 中文 | 0.988 秒 | 200,007 | 93.3 MiB |
| Target 文本规范 | 1.367 秒 | 200,008 | 93.2 MiB |
| Target 为空 | 0.005 秒 | 10 | 43.5 MiB |

根因是多数检查按 `range(start_row, last_row + 1)` 扫描，并通过 `worksheet[...]` 访问
空位置，openpyxl 会因此创建空单元格。新空译文检查使用已有单元格迭代，避开了这个问题。
表中单元格数包含临时报告，但报告只有表头，几乎所有增量都来自输入表被稠密化。

### 长文本

将普通场景的每段 Source / Target 重复 20 次，共 2,000 行，3 次中位数：术语
1.460 秒、数字 1.389 秒、Tag 0.454 秒、文本规范 0.575 秒、URL 0.211 秒。
因此性能还取决于字符数和标记密度，不能只按 Excel 行数估算。

### 密集子串与词表规模

密集子串用 `中` 重复 3、4、5……次作为 Source，Target 对应重复 `译`，所有翻译都正确，
每个规模测一次：

| 行数 | 耗时 | 问题数 | 峰值 RSS |
|---|---:|---:|---:|
| 100 | 0.176 秒 | 0 | 43.6 MiB |
| 200 | 1.486 秒 | 0 | 43.8 MiB |
| 400 | 10.764 秒 | 0 | 44.4 MiB |
| 800 | 79.515 秒 | 0 | 46.9 MiB |

当前实现已经用 Aho-Corasick 索引、按不同 Source/Target 组合检查，也没有保留全局包含关系图。
但 `_matches` 仍会吐出每个模式的每个命中位置，随后 `children` / `present` 才去重。
在这组重复字符输入中，单行会产生平方级的命中位置，总枚举数量可达行数的立方级。
这里行数和单行长度同时增长，不能泛化为固定长度普通文本的复杂度；但它证明了真实的
输入密度风险，而且不是报告问题太多导致的。

术语场景固定 5 万行，把候选词表规模从 100 提高到 10,000，耗时中位数从 3.128 秒升至
10.288 秒，大词表 3 次范围 8.986–13.561 秒，峰值 RSS 117.6 MiB。
增长包括收集词表、建索引、写术语表等多项成本，不能将差值全部归因于某一行代码。
审查发现每个标记数量一致的行都会执行 `candidate_term_mapping = dict(term_mapping)`，
这是随行数 × 已收集词表大小增长的额外工作。
额外一次 `--trace-term-copies` 诊断保持 `dict` 构造结果不变，只计时该模块的这一个构造调用：
在 5 万行 / 1 万词表中，复制累计 2.086 秒，占这次总耗时 12.171 秒约 17%。
该插桩运行有计时开销，只用于确认成本来源；它不是优化后的收益测量。

## 热点与优化优先级

使用 cProfile 对 1 万行普通场景采样得到以下调用证据。累计时间包含子调用，不能跨行相加，
比例也不等于移除该函数后可获得的加速比。

| 检查 | 已观察到的重复处理 |
|---|---|
| 术语 | `extract_term_details` 调用 39,800 次，`strip_supported_marks` 20,000 次，`normalize_text` 96,259 次，`normalize_mark_styles` 59,601 次 |
| 数字 | `extract_numbers` 20,000 次，其中 Tag 提取也调用 20,000 次；Tag 提取占该项带 profiler 总时间约 37% |
| Tag | 构造 Counter 87,076 次；其累计成本约占该项带 profiler 总时间 21% |
| Target 文本 | 配对检查占该项带 profiler 时间约 43%；Token 提取 18,800 次，规则归一化 10,001 次 |
| 大分组报告 | 8,000 行剖析中 `Cell.check_string` 累计约 1.272 秒，总计约 2.027 秒；与报告阶段的内存突增一致 |

以下为首次评估时提出的建议。前四项及规则配置、数字 Counter 复用已实施，实测结果见上方；
跨规则文本缓存、Tag Counter 分组和直接输出结构化问题仍是后续候选。

| 优先级 | 建议 | 适用场景与约束 |
|---|---|---|
| 高 | 工作流跳过最终不会使用的“同组行号”长列；单工具报告按组处理长度上限，避免每个单元格重复截断出新字符串 | 已测出 8,000 行组达到约 561 MiB；保留单工具字段及工作流问题顺序 |
| 高 | 子串匹配避免重复枚举同一模式的每个位置；对高重复密度增加保持完整判定的算法分支 | 已测出 800 行零问题仍需约 80 秒；不能只取最长匹配、截断参考条目或跳过检查，必须保留所有不同子串关系 |
| 中高 | 统一遍历真实存在的数据行，读空位置时不创建单元格 | 稀疏表只有两行仍扩成 10 万 / 20 万单元格；需保留行号、统计口径、原有行顺序、空字符串与公式处理 |
| 中高 | 术语以“本行增量”验证并提交映射，复用已归一化文本与已解析标记 | 大词表更重要；必须保留整行事务、同一行内冲突和历史 TB 优先级 |
| 中 | 将固定配置的归一化、规则选择移到循环外；数字掩码无区间时直接复用字符串；复用 Counter | 主要减少数字、文本规范、Tag 的日常开销，实施面相对小 |
| 中 | 对重复文本和 Token 提取做容量受限的缓存，或共享一次工作流内的预处理 | Cache key 要包括原始/归一化文本与规则配置；数字使用 NFKC，Tag、URL 与配对不能无条件共享位置。需防止缓存反而扩大大表内存 |
| 低 | 进一步消除临时问题表，规则直接返回结构化问题，由统一报告一次写入 | 架构改动较大，普通 5 万行中临时表只占约 3%；应先解决已确认的大分组长列 |
| 低 | 单独微调换行、Target 中文、空译文、简单空格检查 | 普通数据耗时较低；共享行迭代的优化会顺带改善它们 |

另外两处代码级边界值得后续验证，但未计入本轮实测结论：
`select_longest_non_overlapping_matches` 对已接受区间逐个判断重叠，候选区间很多时可能平方增长；
URL 的 `_trim_url` 在大量尾部右括号时反复 `count` 和切片，也可能出现平方增长。
用户自定义正则的耗时取决于具体表达式，不能由默认规则基准代表。

后续优化继续以相同输入的问题集合、问题描述、统计值、行顺序和输出契约等价为验收条件，
再运行同组基准。不建议直接并行全部检查，它们共享并修改同一个 openpyxl 工作簿。

## 可复现命令

以下是开发诊断脚本，不是新增的正式 `qatools` 命令。
默认结果写到 `outputs/qa-performance/`；生成的工作簿位于临时目录并自动关闭、删除。
原始 JSON 和日志是本地诊断产物，不提交生成的 Excel。
首次评估共完成 188 次测量（含剖析与复制计时），没有超时或执行失败；较大的边界场景仅测一次，
已在对应表格说明，不能与重复 3 次的普通基准混作同一统计口径。
优化后另完成 48 次普通单项、16 次稀疏单项测量及 28 次新旧交替对照，无执行失败。
下列命令运行所在检出中的代码；复现旧版需使用 `3db6de8` 的业务代码并复制同一基准脚本，
分别保存新旧结果，避免覆盖原始数据。

```powershell
# 全部单项：普通场景
python scripts/benchmark_qa.py --rows 10000 50000 --repeat 3

# 完整工作流：default 为默认配置；all 额外开启反向和子串一致性
python scripts/benchmark_qa.py --mode workflow --rows 10000 50000 --repeat 3 --output outputs/qa-performance/workflow.json
python scripts/benchmark_qa.py --mode workflow --rows 10000 --errors 0 --repeat 3 --output outputs/qa-performance/workflow-clean.json
python scripts/benchmark_qa.py --mode workflow --rows 10000 --errors 100 --repeat 3 --output outputs/qa-performance/workflow-errors.json

# 大分组；反向检查改为 target-group / target
python scripts/benchmark_qa.py --scenario source-group --check source --rows 1000 2000 4000 8000 --repeat 3 --output outputs/qa-performance/source-group.json

# 仅有两行数据、行跨度 10 万的稀疏工作表
python scripts/benchmark_qa.py --scenario sparse --rows 100000 --repeat 1 --output outputs/qa-performance/sparse.json

# 长文本、密集子串、大词表
python scripts/benchmark_qa.py --scenario long --check term --check number --check tag --check text --check url --rows 2000 --repeat 3 --output outputs/qa-performance/long.json
python scripts/benchmark_qa.py --scenario substring-dense --check substring --rows 100 200 400 800 --repeat 1 --timeout 90 --output outputs/qa-performance/substring-dense.json
python scripts/benchmark_qa.py --check term --rows 50000 --vocabulary 10000 --repeat 3 --output outputs/qa-performance/vocabulary-large.json
python scripts/benchmark_qa.py --check term --rows 50000 --vocabulary 10000 --repeat 1 --trace-term-copies --output outputs/qa-performance/term-copies.json

# 剖析热点，不作为常规耗时基准
python scripts/benchmark_qa.py --check term --check number --check tag --check text --rows 10000 --profile --repeat 1 --output outputs/qa-performance/profiles.json
python scripts/benchmark_qa.py --scenario source-group --check source --rows 8000 --profile --repeat 1 --output outputs/qa-performance/group-profile.json
```
